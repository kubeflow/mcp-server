# KEP-181: Model Registry (Hub) Client Support for kubeflow-mcp-server

## Summary

This KEP proposes implementing the **Hub client module** for
`kubeflow-mcp-server`, wrapping `kubeflow.hub.ModelRegistryClient` to expose
Kubeflow Model Registry operations as 7 MCP tools: 5 read-only discovery tools
and 2 mutating tools behind the standard confirm gate.

This fills the Phase 3 `hub` slot already present in `CLIENT_MODULES`
(module: `kubeflow_mcp.hub`, currently a stub) and closes the gap after
training: an agent that finishes a TrainJob can record the resulting model,
its version and its storage location in the registry, then look it up again
later, without leaving the MCP session. This completes the
`train -> register -> serve` lifecycle up to the point where a serving layer
(KServe) takes over.

## Motivation

### Problem Statement

AI IDEs and orchestrator agents currently have no structured way to:

1. Record a trained model and its artifact location once a training job completes
2. Discover which models and versions already exist in the registry
3. Inspect a specific version's metadata and storage details (the fields
   KServe needs to serve it)
4. Compare versions of a model before choosing one
5. Keep version metadata (descriptions, evaluation metrics, tags) up to date

Without this, an agent reaches "training complete" and hits a dead end.

The existing stub (`kubeflow_mcp.hub`) declares 7 planned tools with
`status: "stub"` but contains no implementations.

### Architecture Context

```
CLIENT_MODULES = {
    "trainer": "kubeflow_mcp.trainer",      # Phase 1: Implemented
    "optimizer": "kubeflow_mcp.optimizer",  # Phase 2: KEP-34 / #105
    "hub": "kubeflow_mcp.hub",              # Phase 3: This KEP (7 tools)
}
```

The `--clients hub` CLI flag already exists. When the hub module exposes a
non-empty `TOOLS` list, `server.py` registers its tools with the existing
audit, rate-limiting, circuit-breaker, persona-filtering and read-only
infrastructure, and picks up the module's descriptions, annotations,
resources and instruction sections through the module contract in
`docs/CONVENTIONS.md`.

Unlike the trainer and optimizer, the Model Registry is **not a Kubernetes
API**. It is a separate REST service reached over HTTP(S), so this module
talks to a configured registry endpoint rather than to the cluster through
kubeconfig (see Key Design Decisions).

### SDK Compatibility

| Component | Version | Notes |
|-----------|---------|-------|
| `kubeflow` (unified SDK) | `>=0.5.0,<0.6.0` | `kubeflow.hub.ModelRegistryClient`; 0.5.0 adds `storage_config` to `register_model()` and the `StorageConfig` type. Pending #195 / #201 |
| `kubeflow[hub]` extra | `model-registry>=0.3.14,<0.4` | Pinned by the SDK's `hub` extra; already part of this repo's `hub` / `all` extras |
| Kubeflow Model Registry | server reachable over HTTP(S) | No CRD dependency |

`ModelRegistryClient` exists in 0.4.x as well, but 0.4.1's `register_model()`
has no storage parameters, so `register_model` could not record how KServe
should fetch the artifact. Implementation therefore targets 0.5.0 and starts
after #195 lands.

> **Note: client class.** Verified against `kubeflow==0.5.0` on PyPI and
> `kubeflow/sdk` `main`: `kubeflow.hub` exports `ModelRegistryClient`,
> `StorageConfig`, `S3UploadParams`, `OCIUploadParams` and `upload_artifact`.
> There is no `HubClient`. If a unified hub client is introduced upstream
> later, only the client factory and the SDK mapping table change; the MCP
> tool surface in this KEP does not depend on the class name.

## Goals

- Implement 7 MCP tools across three phases: `hub_discovery`,
  `hub_registration` and `hub_lifecycle`
- Use `kubeflow.hub.ModelRegistryClient` as the only backend; no direct REST
  calls to the registry
- Two-phase confirmation (`confirmed: bool = False`) for both mutating tools
- MCP ownership marker on registered versions, enforced for non-admin
  personas on mutation, consistent with the trainer's ownership gate
- Follow the full module contract (`TOOLS`, `CLIENT_TOOL_DESCRIPTIONS`,
  `CLIENT_TOOL_ANNOTATIONS`, `CLIENT_RESOURCES`, `INSTRUCTION_SECTIONS`,
  `PHASE_TO_SECTION`, `SECTION_ORDER`) and register tools in `TOOL_PHASES`,
  `TOOL_NEXT_HINTS`, `core/policy.py` and `SDK_COMPATIBILITY`
- A `hub://guides/model-lifecycle` resource describing the train -> register
  -> inspect workflow
- Co-located unit tests, SDK contract tests, persona tests, and a schema
  snapshot that covers the hub tools
- Ship in two PRs: read-only tools first, then the mutating tools

## Non-Goals

- **`promote_model`**: Model Registry has no stage/environment concept.
  `RegisteredModel` and `ModelVersion` carry only `state` (`LIVE`/`ARCHIVED`)
  and free-form `custom_properties`. Inventing a convention such as
  `custom_properties["stage"] = "production"` would become de facto API the
  moment it merged. Deferred until the registry offers a first-class
  promotion API (agreed in #181).
- **Archiving / changing `state`**: `update_model_metadata` does not change
  `state`. A dedicated `archive_model` tool can follow if needed.
- **Artifact upload** (`kubeflow.hub.upload_artifact`): requires local files
  on the server's filesystem and raw storage credentials
  (`S3UploadParams.access_key_id` / `secret_access_key`), neither of which
  should cross the MCP boundary. Models must already be in remote storage.
- **Editing artifacts** (`update_model_artifact`): changing a registered
  artifact's URI or storage settings after registration is out of scope.
- **Serving**: creating KServe `InferenceService`s is a separate client.
  This module returns the fields a serving tool would need.
- **Lineage tracking** (listed under ROADMAP Phase 6): not exposed by
  `ModelRegistryClient`. Follow-up work.
- **Automatic discovery of a TrainJob's output location**: the trainer
  module does not expose where a job wrote its model, so the agent passes
  `uri` explicitly to `register_model`.
- **Comparing versions across different models**: `compare_models` compares
  versions of one registered model.

## Proposal

### Module Structure

```
kubeflow_mcp/hub/
  __init__.py            # MODULE_INFO, TOOLS, descriptions, annotations,
                         # resources, instructions, PHASE_TO_SECTION, SECTION_ORDER
  api/
    __init__.py          # Re-exports
    discovery.py         # list_models, get_model, list_model_versions,
                         # get_model_version, compare_models
    registration.py      # register_model
    lifecycle.py         # update_model_metadata
    architecture_test.py # metadata + persona matrix (trainer pattern)
    sdk_contracts_test.py
    *_test.py            # co-located unit tests
  resources/
    model-lifecycle.md   # train -> register -> inspect workflow guide
```

> **Stub alignment**: the existing stub plans `get_model_artifact` and
> `update_model`, and does not plan `compare_models`. This KEP follows the
> tool list agreed in #181: `update_model` becomes `update_model_metadata`
> (it edits metadata only, on a model or a version), `compare_models` is
> added, and the artifact lookup is folded into `get_model_version` rather
> than exposed as a separate tool (see Key Design Decisions). The stub's
> suggested `api/registration.py` / `api/discovery.py` split is kept, with
> `lifecycle.py` added to match the trainer's phase layout.

### Key Design Decisions

**1. Connection configuration (`HubConfig`).** `ModelRegistryClient` cannot
be created without arguments: its constructor requires `base_url`, and the
underlying `model_registry.ModelRegistry` requires an `author` and performs a
connectivity check (it fetches one page of registered models) inside
`__init__`. The stub's suggested factory (`ModelRegistryClient()`) would
therefore fail. This KEP adds a `HubConfig` section to `core/config.py`,
alongside the existing `TrainerConfig` and `OptimizerConfig`:

| Field | Env override (proposed) | Default | Notes |
|-------|------------------------|---------|-------|
| `url` | `KUBEFLOW_MCP_HUB_URL` | none (required when `hub` is enabled) | Scheme decides TLS: `https://` secure, `http://` insecure |
| `port` | `KUBEFLOW_MCP_HUB_PORT` | inferred from scheme | Passed through to the SDK |
| `author` | `KUBEFLOW_MCP_HUB_AUTHOR` | `"kubeflow-mcp"` | Recorded as author/owner on registrations |
| `custom_ca` | `KUBEFLOW_MCP_HUB_CUSTOM_CA` | none | Path to a PEM CA bundle |
| user token | `KUBEFLOW_MCP_HUB_TOKEN` | none | When unset, `model-registry` falls back to the in-cluster service-account token |

Credentials come only from server configuration. No tool accepts a URL,
token or CA, so an agent cannot redirect the server to another registry or
see credentials.

**2. Lazy client factory.** `get_hub_client()` is added to `common/utils.py`
(convention: `get_<client>_client()`), cached with `@lru_cache(maxsize=1)`
like `get_trainer_client()`. Because construction performs a network call,
the client is created on the first hub tool call, never at import or server
start. `lru_cache` does not cache exceptions, so a registry that is down at
first use is retried on the next call instead of being cached as broken.
`reset_clients()` clears it. `kubeflow.hub` is only imported when
`--clients hub` is active.

**3. No namespaces.** The registry is not a Kubernetes resource, so hub tools
take no `namespace` parameter, and `check_namespace_allowed()` /
`validate_k8s_name()` do not apply. Model and version names are validated as
non-empty, bounded-length strings without control characters instead of as
Kubernetes names.

**4. MCP ownership marker.** `docs/CONVENTIONS.md` requires that non-admin
personas only mutate MCP-created resources. Registry objects have no labels,
so the marker is stored as a custom property using the existing constants:
`custom_properties["kubeflow-mcp/managed-by"] = "mcp"`
(`MCP_MANAGED_LABEL` / `MCP_MANAGED_VALUE`).

- `register_model` adds the marker to the new version's `metadata`. When the
  call also creates the registered model (it did not exist before), the
  marker is added to the model with a follow-up `update_model` call.
- `update_model_metadata` requires the marker on its target for every
  persona except `platform-admin`, mirroring the trainer's
  `_require_mcp_ownership`. Missing target returns `RESOURCE_NOT_FOUND`;
  target without the marker returns `VALIDATION_ERROR` (convention).
- The marker key is reserved: `update_model_metadata` rejects any attempt to
  set or remove it.

**5. `register_model` inputs.** Parameters: `name`, `uri`, `version`,
`model_format_name`, `model_format_version`, `version_description`,
`metadata`, and the three `StorageConfig` fields flattened as
`storage_key`, `storage_path`, `service_account_name`. These three are
*names* of a Kubernetes Secret, a bucket sub-path and a ServiceAccount, not
credentials, so they are safe to accept. `author` and `owner` are not tool
parameters; they come from `HubConfig.author`, so an agent cannot attribute a
registration to someone else. `uri` must include a scheme and must not embed
credentials (URIs with a userinfo part, `user:pass@host`, are rejected).

The SDK's `register_model()` reuses an existing registered model with the
same name and raises if the version already exists. The preview therefore
reports which case applies: `creates_model: true` for a new model, or the
existing model's `owner` when adding a version to it. A duplicate version is
reported at preview time as `VALIDATION_ERROR`, not only on confirm.

**6. `update_model_metadata` semantics.** The SDK's update methods take full
objects (`RegisteredModel` / `ModelVersion`), not partial dicts, so the tool
reads the object, applies the change, and writes it back with
`update_model()` or `update_model_version()`; the confirm gate wraps the
final write (agreed in #181). It targets the registered model when `version`
is omitted and that version when it is given. Editable fields are limited to:

- `description`
- `custom_properties`, changed through `set_properties` (merged into the
  existing dict; values must be `bool`, `int`, `float` or `str`, the
  registry's supported types) and `remove_keys` (deleted)

At least one change is required, and a key may not appear in both
`set_properties` and `remove_keys`. Merging (rather than replacing) means an
agent cannot wipe all existing metadata by passing a partial dict.

**7. Stale-write protection.** Read-modify-write can overwrite a concurrent
change made between the preview and the confirmed call. The preview returns
the target's `last_update_time_since_epoch` together with the before/after
diff. The confirmed call accepts an optional
`expected_last_update_time`; when provided, the tool re-reads the target and
aborts with `VALIDATION_ERROR` if the value changed, telling the agent to
preview again. The registry has no conditional-update API, so a small window
between that re-read and the write remains; this narrows the race rather
than eliminating it.

**8. Artifact details folded into `get_model_version`.** Instead of a separate
`get_model_artifact` tool, `get_model_version` also calls
`get_model_artifact(name, version)` and returns the artifact's `uri`,
`model_format_name`, `model_format_version`, `storage_key`, `storage_path`
and `service_account_name`. One call gives an agent everything needed to
hand the model to a serving layer, and the tool count stays at the 7 agreed
in #181. If the artifact lookup fails, the version is still returned with
`artifact: null` and `artifact_unavailable: true`, so one missing artifact
does not hide the version.

**9. Bounded listings.** `list_models()` and `list_model_versions()` return
lazy pagers over the whole registry. The tools take `limit` (default 50,
max 500) and stop iterating once reached, so large registries are neither
fully fetched nor flooded into the agent's context. Responses include
`count` and `truncated: true` when the limit was hit. An exact total is not
reported, because computing it would require paging through everything.

**10. Response shapes.** All tools return the shared models from
`common/types.py`: `ToolResponse` on success, `PreviewResponse` for
mutation previews, `ToolError` on failure (no stack traces; details via
`exception_details()`). Registry objects are converted to plain dicts;
`custom_properties` is returned as-is.

### MCP Tools

#### Discovery (`hub_discovery`)

| Tool | Parameters | Returns |
|------|-----------|---------|
| `list_models` | `limit=50` | Registered models: `name`, `id`, `owner`, `state`, `description`, update time; `count`, `truncated` |
| `get_model` | `name` | Model details including `custom_properties` |
| `list_model_versions` | `name`, `limit=50` | Versions of the model: `name` (version string), `id`, `author`, `state`, `description`, update time; `count`, `truncated` |
| `get_model_version` | `name`, `version` | Version details plus `artifact` (URI, format, storage fields) |
| `compare_models` | `name`, `versions` (2 to 5) | Per-version summary side by side, plus `differences`: fields and `custom_properties` keys whose values differ |

#### Registration (`hub_registration`)

| Tool | Parameters | Returns |
|------|-----------|---------|
| `register_model` | `name`, `uri`, `version`, `model_format_name?`, `model_format_version?`, `version_description?`, `metadata?`, `storage_key?`, `storage_path?`, `service_account_name?`, `confirmed=False` | Preview (incl. `creates_model`), then the registered model/version |

#### Lifecycle (`hub_lifecycle`)

| Tool | Parameters | Returns |
|------|-----------|---------|
| `update_model_metadata` | `name`, `version?`, `description?`, `set_properties?`, `remove_keys?`, `expected_last_update_time?`, `confirmed=False` | Preview with before/after diff and `last_update_time_since_epoch`, then the updated object |

### Tool Annotations

| Tool | `readOnlyHint` | `destructiveHint` | `idempotentHint` | `openWorldHint` |
|------|---------------|-------------------|------------------|-----------------|
| 5 discovery tools | `True` | `False` | `True` | `True` |
| `register_model` | `False` | `False` | `False` (a repeat call fails on the duplicate version) | `True` |
| `update_model_metadata` | `False` | `False` | `True` | `True` |

Every tool gets a `title` and `tags` that include its phase. There are no
`delete_*` tools, so `DESTRUCTIVE_TOOLS` is unchanged. Because
`server.py` treats any tool without `readOnlyHint: True` as a write tool in
read-only mode, only the 5 discovery tools remain available there.

### Persona Coverage

`core/policy.py` lists tools by name, so each persona gains:

| Persona | Hub tools |
|---------|-----------|
| `readonly` | `list_models`, `get_model`, `list_model_versions`, `get_model_version`, `compare_models` |
| `data-scientist` | readonly + `register_model` |
| `ml-engineer` | data-scientist + `update_model_metadata` (MCP-owned targets only) |
| `platform-admin` | all (wildcard); ownership gate bypassed |

This follows the persona matrix in `docs/CONVENTIONS.md`: `create_*`-style
tools at `data-scientist`, `update_*` at `ml-engineer`.

### Tool Phase Categories

```python
TOOL_PHASES.update({
    "hub_discovery": [
        "list_models", "get_model", "list_model_versions",
        "get_model_version", "compare_models",
    ],
    "hub_registration": ["register_model"],
    "hub_lifecycle": ["update_model_metadata"],
})

PHASE_TO_SECTION = {
    "hub_discovery": "hub_discovery",
    "hub_registration": "hub_registration",
    # lifecycle instructions folded into the registration section
    "hub_lifecycle": "hub_registration",
}

SECTION_ORDER = ["hub_discovery", "hub_registration"]
```

Phase and section names are prefixed with `hub_`. The trainer already owns
`discovery`, `planning`, `monitoring`, `lifecycle` and `training`; adding hub
tools to those shared keys would mix them into the trainer's categories and
instruction sections. `hub_discovery` maps to its own section (rather than
`None`, as the trainer's `discovery` does) because the hub has no planning
section to carry discovery guidance, and `readonly` users need it.

### Instruction Sections

**Discovery** (all personas):
```
MODEL REGISTRY DISCOVERY:
- list_models() -> find registered models
- list_model_versions(name) -> versions of one model
- get_model_version(name, version) -> metadata + artifact URI/format/storage
- compare_models(name, versions=[...]) -> side-by-side diff of 2-5 versions
- See hub://guides/model-lifecycle for the train -> register workflow
```

**Registration** (data-scientist and above):
```
MODEL REGISTRATION:
- After training completes, register the output with
  register_model(name, uri, version, ...). The model must already be in
  remote storage; pass the storage Secret/ServiceAccount NAMES, never keys.
- ALWAYS preview first (confirmed=False); check creates_model and fix
  duplicate versions before confirming.
- update_model_metadata(name, version=None, ...) edits description and
  custom properties only. Preview first, then confirm with
  expected_last_update_time from the preview.
```

| `update_model_artifact(artifact)` | *(none)* | Non-goal |

#### Tools Beyond SDK Abstraction

- **`compare_models`**: the SDK has no comparison method. The tool calls
  `get_model_version` and `get_model_artifact` for each requested version
  and computes the differences itself.
- **`update_model_metadata`**: the SDK has no partial update. The tool
  implements merge/remove semantics and the stale-write check on top of the
  full-object update methods.

### Cross-Client Integration

A typical agent-driven flow spans the trainer and hub clients:

```
pre_flight()                     # Validate cluster
fine_tune(...)                   # Train; the job writes the model to remote storage
wait_for_training(name)          # Wait for completion
register_model(name, uri, version, storage_key=..., confirmed=False)  # Preview
register_model(..., confirmed=True)                                   # Register
get_model_version(name, version) # Artifact URI/format/storage for serving
```

The hub module does not import the trainer module, so `--clients hub` loads
standalone. The trainer's existing `TOOL_NEXT_HINTS` are not changed by this
KEP; the train -> register handoff is documented in the
`hub://guides/model-lifecycle` resource and the hub instruction sections.

## Risks and Mitigations

### Registry Unreachable or Misconfigured

The registry is a separate service; a wrong URL, TLS mismatch or missing
token fails at client construction.

**Mitigations**:
- Lazy construction; failures are not cached (see Key Design Decisions)
- Errors return `ToolError` with a `hint` naming the `HubConfig` settings to
  check, without echoing the token
- The per-tool circuit breaker that `server.py` applies to every tool
  (`core/resilience.py`) covers hub tools as for other clients

### Async Runtime Interaction

`model-registry` runs its async API calls through a sync wrapper: it applies
`nest_asyncio` when the client is constructed and runs each call on the
calling thread's event loop. FastMCP (3.4.x, as locked) executes sync tool
functions in an `anyio` worker thread, and `model-registry` opens a fresh
HTTP client per call, so no connection is shared across event loops.

**Mitigation**: a short spike before PR 1 that exercises the hub tools under
both `stdio` and `http` transports with concurrent calls, plus an integration
test covering the same. If problems appear, calls are funnelled through a
single dedicated worker thread. A custom `async_runner` would be cleaner, but
`ModelRegistryClient` does not expose that parameter today, so it would need
an upstream SDK change.

### Lost Updates on Metadata

Two writers doing read-modify-write on the same object can overwrite each
other.

**Mitigation**: `expected_last_update_time` check on confirm (Key Design
Decision 7). Residual window documented; a conditional-update API upstream
would close it.

### Unintended Registrations

An agent could register models or versions the user did not intend.

**Mitigations**:
- Two-phase confirmation; the preview shows whether a new model is created
- `readonly` persona and read-only mode block both mutating tools
- `author`/`owner` fixed by server config, so registrations are attributable
- Non-admin updates limited to MCP-registered objects

### Credential Exposure

**Mitigations**:
- No tool accepts registry credentials or storage keys
- Storage parameters are Secret / ServiceAccount names only
- `uri` values with embedded credentials are rejected
- `upload_artifact` (which takes raw keys) is a non-goal

### Ownership Marker Key Format

The marker reuses `kubeflow-mcp/managed-by` as a custom-property key.
Custom-property keys are free-form strings in the registry's data model, but
the round-trip of a key containing `/` has not yet been verified against a
live registry.

**Mitigation**: covered by an integration test in PR 1's spike; if it does
not round-trip, a hub-specific constant (for example `kubeflow_mcp_managed_by`)
is used instead and documented.

### SDK Behaviour Changes

`ModelRegistryClient` signals "not found" differently per method
(`ValueError` from `get_model` / `get_model_version`, `StoreError` when the
parent model is missing).

**Mitigation**: SDK contract tests pin these error shapes so an SDK bump that
changes them fails CI instead of silently turning not-found into
`SDK_ERROR`.

## Testing Plan

### Unit Tests

- Each tool in isolation with a mocked `ModelRegistryClient`
- Response shapes (`ToolResponse` / `PreviewResponse` / `ToolError`) and
  error codes: `RESOURCE_NOT_FOUND` for missing models/versions,
  `VALIDATION_ERROR` for bad input, ownership failures and stale writes,
  `SDK_ERROR` otherwise
- `limit`: iteration stops at the limit, `truncated` set correctly, pager
  not consumed past the limit
- `register_model`: preview makes no write; `creates_model` true/false;
  duplicate version rejected at preview; ownership marker added to
  `metadata`; marker added to a newly created model; `StorageConfig` built
  from flattened params; credential-bearing URIs rejected
- `update_model_metadata`: model vs version targeting; merge and remove
  semantics; reserved marker key protected; empty change rejected;
  overlapping set/remove rejected; unsupported value types rejected; stale
  `expected_last_update_time` aborts without writing; confirm gate wraps only
  the final write
- `get_model_version` returns the version when the artifact lookup fails
- `compare_models`: 2-5 versions enforced; differences computed correctly

## Open Questions

1. Should a non-admin persona be allowed to add a version to an existing
   registered model that MCP did not create? This KEP allows it (adding a
   version does not modify existing versions) and shows the existing owner
   in the preview; restricting it to MCP-owned models is a one-line policy
   change.
2. Is `limit` default 50 / max 500 (matching KEP-34) appropriate for
   registries, or should the cap be lower?
3. Any preferred naming for the `HubConfig` environment variables?
