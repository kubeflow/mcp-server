# Releasing kubeflow-mcp

This repository publishes the `kubeflow-mcp` Python package to PyPI and a container
image to GHCR using GitHub Actions. Publishing uses PyPI trusted publishing (OIDC) —
no PyPI API tokens are stored in GitHub secrets.

The flow mirrors the [Kubeflow SDK release process](https://github.com/kubeflow/sdk/blob/main/RELEASE.md):
you bump the version locally, open a PR, and merging it drives the rest automatically.

## Prerequisites

- [Write](https://docs.github.com/en/organizations/managing-access-to-your-organizations-repositories/repository-permission-levels-for-an-organization#permission-levels-for-repositories-owned-by-an-organization)
  permission for the repository.
- A [GitHub token](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)
  exported as `GITHUB_TOKEN` — `make release` uses it so `git-cliff` can attribute
  changelog entries to their pull requests and authors.

## Versioning

Versions follow Python's [PEP 440](https://peps.python.org/pep-0440/): `X.Y.Z`, where
`X` is major, `Y` is minor, and `Z` is patch. Pre-releases use `X.Y.ZrcN` where `N` is
the release-candidate number.

**Single source of truth:** the version lives only in `kubeflow_mcp/__init__.py`
(`__version__`). `pyproject.toml` reads it dynamically via
`[tool.hatch.version]`, so there is no second value to keep in sync. Bump it only
through `make release` (below).

## Release Branches and Tags

- Release branches are `release-X.Y` (e.g. `release-0.1`). `X.Y.Z` releases are cut
  from the matching `release-X.Y` branch, which the workflow creates automatically.
- Tags are the bare version string, e.g. `0.1.0` (no `v` prefix).
- To patch an older minor series, cherry-pick your change onto `release-X.Y` and open a
  PR against that branch.

## Changelog Structure

Changelogs use a directory-based structure under `CHANGELOG/`, one file per minor series:

```
CHANGELOG/
├── CHANGELOG-0.1.md    # All 0.1.x releases
└── CHANGELOG-0.2.md    # All 0.2.x releases
```

Entries are generated by `git-cliff` (configured in `cliff.toml`) and grouped by the
conventional-commit type enforced on PR titles (`feat` / `fix` / `chore` / `revert`).
RC releases skip changelog generation.

## Release Process

### Overview

1. **Local preparation** — `make release VERSION=X.Y.Z` bumps the version and generates
   the changelog.
2. **Open a PR** — review and merge it.
3. **Automated CI** — the `Release` workflow creates/updates the `release-X.Y` branch,
   builds and tests, tags, publishes to PyPI, publishes the Docker image, and creates the
   GitHub Release.
4. **Manual approvals** — PyPI publish and GitHub Release run in the `release`
   environment and require reviewer approval.

### 1. Update version and changelog

```sh
export GITHUB_TOKEN=<your_github_token>
make release VERSION=X.Y.Z      # e.g. make release VERSION=0.1.0
```

This updates:

- `kubeflow_mcp/__init__.py` → `__version__ = "X.Y.Z"`
- `CHANGELOG/CHANGELOG-X.Y.md` → a new top entry `## [X.Y.Z] (YYYY-MM-DD)`
  (skipped for `rcN`)

### 2. Open a pull request

- Review `kubeflow_mcp/__init__.py` and `CHANGELOG/CHANGELOG-X.Y.md`.
- **Latest minor series:** open the PR against `main`.
- **Older minor-series patch** (e.g. `0.1.1` when `main` is on `0.2.x`): check out the
  `release-X.Y` branch and open the PR against it.

### 3. Automated release

Merging the version bump triggers the `Release` workflow (it fires only when
`kubeflow_mcp/__init__.py` changes on `main` or `release-*`). It runs:

1. **Prepare** — creates or updates `release-X.Y` (cherry-picking the bump from `main`).
2. **Build** — runs `make verify` and `make test-python`, verifies the version, builds and
   `twine check`s the distribution.
3. **Tag** — creates and pushes the `X.Y.Z` tag.
4. **Publish to PyPI** — trusted publishing (requires approval).
5. **Publish Docker image** — builds and pushes `ghcr.io/<owner>/<repo>` (see below).
6. **GitHub Release** — attaches the built artifacts and the changelog body (requires
   approval).

A version that is not a valid `X.Y.Z` / `X.Y.ZrcN` string (for example a `-dev`
placeholder) is rejected by the workflow so an accidental bump cannot cut a release.

### 4. Manual approvals

In [GitHub Actions](https://github.com/kubeflow/mcp-server/actions) → `Release`:

1. Approve **Publish to PyPI** (`release` environment).
2. After PyPI succeeds, approve **Create GitHub Release** (`release` environment).

### 5. Final verification

```sh
pip install kubeflow-mcp==X.Y.Z
kubeflow-mcp --version
```

Also confirm the [PyPI project](https://pypi.org/project/kubeflow-mcp/), the
[GitHub Release](https://github.com/kubeflow/mcp-server/releases), and the container image
were published.

## Test PyPI Dry Run

Use this to validate a build end-to-end without touching production. Running the `Release`
workflow via **`workflow_dispatch`** builds the selected ref and publishes **only to Test
PyPI** — it does not create a branch, tag, GitHub Release, or Docker image.

Dispatch is only allowed from `main` or an existing `release-X.Y` branch — the workflow
rejects a dispatch from any other branch. (GitHub Actions ignores a `branches:` filter on
`workflow_dispatch`, so this is enforced by an explicit check instead.) This means the RC
bump must land on `main` (or `release-X.Y`) before you can dry run it — you cannot dispatch
from a feature branch.

1. Bump the version with `make release VERSION=X.Y.ZrcN` and merge it to `main` (or
   `release-X.Y`).
2. Open GitHub Actions → `Release` → `Run workflow`, select `main` (or the `release-X.Y`
   branch), and enter the expected version string (validated against
   `kubeflow_mcp/__init__.py`).
3. Approve the `test-pypi` environment.
4. Verify the upload:

   ```sh
   pip install \
     --index-url https://test.pypi.org/simple/ \
     --extra-index-url https://pypi.org/simple/ \
     kubeflow-mcp==X.Y.ZrcN
   kubeflow-mcp --version
   ```

## Docker Image

The container image is built and pushed to GHCR by the release workflow, which calls the
reusable [`docker-publish.yaml`](../../.github/workflows/docker-publish.yaml) after tagging.
Because tags pushed by the workflow's `GITHUB_TOKEN` cannot retrigger a tag-push workflow,
the release job invokes it directly rather than relying on a tag trigger.

Image tags:

| Release type | Tags pushed |
| --- | --- |
| Stable `X.Y.Z` | `X.Y.Z`, `X.Y`, `X`, `latest` |
| Pre-release `X.Y.ZrcN` | `X.Y.ZrcN` only (no moving tags, no `latest`) |

Pull requests still build the image for validation but do not push. A maintainer can also
run `docker-publish.yaml` manually via `workflow_dispatch` with a `version` input to
rebuild a specific tag.

## Local Testing

Run these from the repository root before releasing.

1. Lint, format, and unit tests:

   ```sh
   make verify
   make test-python
   ```

2. Build and validate the distribution:

   ```sh
   rm -rf dist/
   uv build
   uvx twine check dist/*
   ```

3. Inspect the wheel in a clean virtual environment:

   ```sh
   python -m venv /tmp/kubeflow-mcp-release-test
   /tmp/kubeflow-mcp-release-test/bin/python -m pip install --upgrade pip
   /tmp/kubeflow-mcp-release-test/bin/python -m pip install dist/*.whl
   /tmp/kubeflow-mcp-release-test/bin/kubeflow-mcp --version
   /tmp/kubeflow-mcp-release-test/bin/python -c "import kubeflow_mcp; print(kubeflow_mcp.__version__)"
   rm -rf /tmp/kubeflow-mcp-release-test
   ```

Trusted publishing cannot be exercised locally because it depends on GitHub Actions OIDC
tokens and the configured environments — use the Test PyPI dry run for that.

## Trusted Publisher Setup

Configure trusted publishing for both PyPI and Test PyPI. The workflow uses `id-token: write`
and reads no PyPI token from secrets.

For PyPI, add a publisher for the `kubeflow-mcp` project:

| Field | Value |
| --- | --- |
| Owner | `kubeflow` |
| Repository name | `mcp-server` |
| Workflow name | `release.yaml` |
| Environment name | `release` |

For Test PyPI, add a publisher for the `kubeflow-mcp` project:

| Field | Value |
| --- | --- |
| Owner | `kubeflow` |
| Repository name | `mcp-server` |
| Workflow name | `release.yaml` |
| Environment name | `test-pypi` |

Create matching GitHub environments named `release` and `test-pypi`, and configure required
reviewers on each so publishing waits for manual approval.
